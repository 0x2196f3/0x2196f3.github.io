build: 69e62fc77 (10206)

  • pp512(prompt processing): 处理512个输入tokens的速度.
    瓶颈在GPU矩阵计算性能.

  • tg512(token generation): 输出512个tokens的速度.
    每生成一个token,理论上要将模型的所有权重从显存读入GPU核心进行运算,所以显存带宽是严重的瓶颈.

## llama.cpp参数优化

## 1. -c 8192 设定上下文长度

由于内存带宽不足导致推理速度慢, 8192(8k)已经很难用完, 相比默认256k可大幅降低内存占用.

## 2. --reasoning-budget 0 设定思考消耗tokens上限

设置为0可关闭大部分模型的思考模式,减少上下文长度和输出耗时.

  • gpt-oss官方表示无法关闭思考,但目前可以完全关闭
  • qwen3-30b-a3b-2507 分为Instruct和Thinking两个版本,Thinking在旧版本llama.cpp和ollama无法关闭思考.
    目前它虽然不输出<think>标识,但内容还是<think>里面的内容
  • 新模型gemma4或qwen3.6完全正常
  • 如果不设置也可以由用户通过API控制

## 3. -lm (–load-mode) 模型加载到内存的方式

llama.cpp的内存主要分为两部分

  1. 模型内存: 硬盘中model.gguf在内存中的副本
    • 只读
    • 每生成一个token就要将整个模型从内存读取到CPU进行计算
  2. 上下文内存: 用户输入的tokens和已经输出的tokens (KV Cache)
    • 在推理过程中需要频繁读写
    • 如果内存严重不足(比如模型本身就大于内存容量),KV Cache会被频繁SWAP到磁盘,严重损耗磁盘寿命
  • -lm设置的内存工作模式只对存储模型权重的内存生效,KV Cache不受-lm控制.
模式说明
mmap (默认)使用mmap()将文件映射到虚拟内存并按需加载进物理内存. 内存不足时直接从物理内存清除. 由于模型只读,内存中的内容只是硬盘文件的映射,所以模型内存永远不会进入SWAP. 多个进程可共享同一个gguf文件的映射,只占一份内存.
mmap + mlockmmap()功能同上,但强制OS将模型内存全部加载到物理内存,如果内存不足,直接OOM退出
none使用malloc()将文件读入进程私有内存,不可共享.如果内存不足,模型可能会被SWAP到硬盘,导致大量硬盘写入.
mlock (none+mlock)malloc()功能同上,但强制OS将模型内存全部加载到物理内存且不可被SWAP,如果内存不足,直接OOM退出
dio使用GPU推理,将模型加载到GPU VRAM时,不在内存中保留副本,可以大幅节约内存

### 4. -ngl 999 使用GPU推理时模型加载到GPU的层数,

  • 其余Layers使用CPU推理
  • 设置为一个极大值999使得模型永远在GPU推理
    (VRAM不足时使用内存作为共享VRAM,推理时先读进GPU VRAM再由GPU推理)

### 5. --spec-type draft-mtp --spec-draft-n-max 2 -md mtp.gguf 开启MTP

  • 在GPU上MoE模型能有小幅度提速
  • 据说对于dense模型能有数倍的提速
  • 使用多个不同型号的CPU测试,开启MTP都会降速

## llama.cpp编译期优化

  • C++编译器只能优化在CPU上执行的指令的效率,要优化GPU执行效率,建议使用Nvidia/TensorRT-LLM(只支持Nvidia GPU)

# 在本机编译(开启Native)

绝大部分和LLM推理有关的代码会被编译到libggml*.so
目前llama.cpp的release已经打包了大量针对不同CPU架构优化的libggml-cpu,比如libggml-cpu-alderlake.so,会自动调用alderlake支持的先进指令集(如AVX2,AVX_VNNI)加速计算.

使用objdump可以看到libggml-cpu-alderlake.so使用了AVX_VNNI指令集,而libggml-cpu-skylakex.so的没有.

objdump -d libggml-cpu-alderlake.so | grep -E 'vpdpbusd|vpdpbusds|vpdpwssd|vpdpwssds|vpdpssd|vpdpbdd|vpdpbudd|vpdpsdd'
  • 由于官方版本已针对先进指令集优化,在本机编译并开启-DGGML_NATIVE=ON的性能提升很小
后端pp512 (t/s)tg512 (t/s)
llama.cpp official (libggml-cpu-alderlake.so)81.54 ± 0.4314.52 ± 0.01
native (-DGGML_NATIVE=ON -DGGML_LTO=ON)82.19 ± 0.2214.69 ± 0.11

# 使用BLAS代替libggml-cpu

(BLAS=Basic Linear Algebra Subprograms,基础线性代数程序集)
是一个关于矩阵运算的标准,不同厂商可以有不同的实现

在编译时期开启-DGGML_BLAS=ON,则LLM推理的计算不再调用libggml-cpu-*.so,而是交由指定的BLAS库执行

## llama.cpp支持的BLAS库 llama.cpp/docs/build.md

OpenBLAS
BLIS
Intel oneMKL

  • 由于大部分BLAS库是预编译的二进制文件(*.so),编译llama.cpp时BLAS库本身不会从头编译,而是直接引用下载的so,所以无论编译llama.cpp时如何设置参数,BLAS库本身的性能不会有太大区别.
  • 高性能BLAS库的so会对不同CPU架构做针对性的优化,所以不用担心没有在本机编译性能会下降.

### 结论

  • 性能只和编译器有关,和BLAS无关.
  • 推测Q4量化的模型根本不会调用BLAS库,因为BLAS不支持Q4,只支持FP32这类传统数据类型
  • 使用CPU运行LLM受限于内存带宽,不可能用fp16或fp32的模型,所以使用BLAS没有意义

# 使用Intel ICX编译器代替GCC

  • 硬件,软件,模型同上
  • 不使用BLAS

### 1. -ipo

-DCMAKE_C_FLAGS="-O3 -march=${MARCH} -ipo" \ 
-DCMAKE_CXX_FLAGS="-O3 -march=${MARCH} -ipo" \
  • 编译报错

### 2. -x${MARCH}

针对特定架构CPU优化,开启后编译出的文件无法在非Intel CPU上执行(原理是运行时主动检测CPU型号,不是Intel就直接退出).
由于llama.cpp在编译时会先编译一些临时二进制文件,再在本机执行它们进行后续操作,所以开启-x后无法在AMD平台编译.

参数pp512 (t/s)tg512 (t/s)
-xraptorlake95.89 ± 0.1315.05 ± 0.05
-march=raptorlake95.43 ± 0.2415.34 ± 0.01
  • 0.3的差距不是误差,确实有变化.
  • 会导致无法使用Github Actions编译(Github的Runner很多是AMD CPU)

### 3. -fp-model=fast

通过牺牲浮点数的计算准确度加速运算.理论上对模型输出的质量有影响

参数pp512 (t/s)tg512 (t/s)
-march=raptorlake -fp-model=fast95.33 ± 0.3415.32 ± 0.00
-march=raptorlake95.43 ± 0.2415.34 ± 0.01
  • 可以编译成功,但性能没区别,可能根本不支持q4量化的模型.
  • 没有必要继续测试模型智力的损失

# Intel ICX依赖问题

Intel ICX编译的llama.cpp会引用Intel自己的so,无法直接在普通ubuntu上运行
最简单的方法是使用Intel提供的docker image

  • 编译环境: intel/oneapi-toolkit(下载3.4GB)
  • 运行环境: intel/oneapi-runtime(下载2GB)

得益于docker优秀的分层设计,只要oneapi-runtime版本不变,llama.cpp更新时就不用重新下载几GB的image.

# 编译llama.cpp:server的Dockerfile

  • 目前oneapi-runtime还没有2026.1.0版本,如果有可以将final image替换为docker.io/intel/oneapi-runtime:2026.1.0-devel-ubuntu$UBUNTU_VERSION
ARG UBUNTU_VERSION=24.04
ARG MARCH=alderlake
ARG APP_VERSION=b10156

FROM docker.io/intel/oneapi-toolkit:2026.1.0-devel-ubuntu$UBUNTU_VERSION AS build

ARG MARCH
ARG APP_VERSION

RUN apt-get update && \
    apt-get install -y gcc-14 g++-14 build-essential git cmake libssl-dev jq wget curl

ENV CC=gcc-14 CXX=g++-14

WORKDIR /app

RUN if [ -n "${APP_VERSION}" ]; then \
      TAG="${APP_VERSION}"; \
    else \
      TAG=$(curl -s "https://api.github.com/repos/ggml-org/llama.cpp/releases/latest" | jq -r .tag_name); \
    fi && \
    git clone https://github.com/ggml-org/llama.cpp.git . && \
        git fetch --tags && \
        git checkout "tags/${TAG}"

RUN cmake -S . -B build \
            -DCMAKE_C_COMPILER=icx \
            -DCMAKE_CXX_COMPILER=icpx \
            -DCMAKE_C_FLAGS="-O3 -march=${MARCH}" \
            -DCMAKE_CXX_FLAGS="-O3 -march=${MARCH}" \
            -DCMAKE_BUILD_TYPE=Release \
            -DGGML_NATIVE=OFF \
            -DGGML_LTO=ON \
            -DLLAMA_BUILD_TESTS=OFF \
            -DGGML_BACKEND_DL=ON \
            -DGGML_CPU_ALL_VARIANTS=OFF && \
    cmake --build build -j $(nproc)

RUN find /app -type f -name "*.so*" -exec strip --strip-unneeded {} \; 2>/dev/null || true

RUN mkdir -p /app/lib && \
    find build -name "*.so*" -exec cp -P {} /app/lib \;

RUN mkdir -p /app/full \
    && cp build/bin/* /app/full \
    && cp *.py /app/full \
    && cp -r conversion /app/full \
    && cp -r gguf-py /app/full \
    && cp -r requirements /app/full \
    && cp requirements.txt /app/full \
    && cp .devops/tools.sh /app/full/tools.sh

FROM docker.io/intel/oneapi-toolkit:2026.1.0-devel-ubuntu$UBUNTU_VERSION AS final

RUN apt-get update \
    && apt-get install -y libgomp1 curl ffmpeg \
    && apt autoremove -y \
    && apt clean -y \
    && rm -rf /tmp/* /var/tmp/* \
    && find /var/cache/apt/archives /var/lib/apt/lists -not -name lock -type f -delete \
    && find /var/cache -type f -delete

ENV LLAMA_ARG_HOST=0.0.0.0

COPY --from=build /app/lib/ /app
COPY --from=build /app/full/llama /app/full/llama-server /app

WORKDIR /app

HEALTHCHECK CMD [ "curl", "-f", "http://localhost:8080/health" ]

ENTRYPOINT [ "/app/llama-server" ]
